# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Daily stock-analysis pipeline for the top-20 Moscow Exchange (MOEX) tickers. Pulls quotes/history from the MOEX ISS API, scores each stock on three pillars (fundamental, technical, sentiment), emits BUY/HOLD/SELL signals with a 4-week target price, generates a Russian-language report via the Claude API, and pushes it to Telegram. Runs unattended Mon-Fri via GitHub Actions.

Code comments and log messages are in Russian — keep that convention when editing.

## Commands

```bash
pip install -r requirements.txt   # deps: requests, pandas, numpy, anthropic (+ pytest for tests)
python main.py                    # run full pipeline (entry point)
pytest                            # run unit tests (tests/)
pytest tests/test_scoring.py::test_target_price   # run a single test
python backtest.py --ticker SBER  # walk-forward backtest of the technical pillar
python backtest.py --horizon 28   # evaluate stored runs vs realized forward returns
python dashboard.py               # rebuild docs/index.html from stored runs
```

Tests live in [tests/](tests/) and are network-free (MOEX/Claude calls are monkeypatched). No linter or build step. Python 3.11 (matches CI). No virtualenv committed.

To run a single stage in isolation, import its module functions in a REPL — every stage is a pure function taking plain dicts/DataFrames (see signatures in `analysis/`, `scoring/`). The pipeline degrades gracefully: missing API keys or failed network calls log a warning and fall back to a neutral score (50) rather than crashing.

## Configuration

All secrets come from env vars (`.env` locally, GitHub Secrets in CI): `ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Without them the pipeline still runs — sentiment/report fall back, and the report prints to console instead of Telegram.

[config.py](config.py) is the single source of truth for tunables: the `TOP20_TICKERS` list and `COMPANY_NAMES` map (update quarterly), pillar `WEIGHTS` (must sum to 1.0), `SIGNAL_THRESHOLDS`, MOEX board/retry settings, and `CLAUDE_MODEL`. It auto-creates `reports/` and `logs/` on import.

## Architecture

Pipeline orchestrated by [main.py](main.py) `run_pipeline()`: fetches fundamentals + a batch quotes call, then fans out per-ticker work across a `ThreadPoolExecutor` (`TICKER_MAX_WORKERS`, I/O-bound: history + Claude). Each ticker is handled by `_process_ticker`, which runs the three pillars and returns `(result, meta)`; `meta` feeds an end-of-run summary line (skipped/errors/fallbacks) so silent degradation is visible. Per ticker:

1. **Data** ([data/moex_api.py](data/moex_api.py)) — MOEX ISS API client. All HTTP goes through `_get()` (3 retries × 5s, returns `None` on failure, never raises). Functions: `get_current_quotes` (parses the `marketdata` section), `get_history` (returns a `pd.DataFrame`), `get_dividends`/`calc_div_yield`, `get_index_composition`.
2. **Technical** ([analysis/technical.py](analysis/technical.py)) — RSI/MACD/SMA/volume/volatility computed in pure pandas+numpy (no TA libs). `compute_indicators(df)` → dict; `score_technical(dict)` → 0–100. Insufficient data returns neutral defaults via `_empty_indicators()`. Before computing, `trim_price_gap` cuts history at the last day-over-day CLOSE gap > `PRICE_GAP_THRESHOLD` (40%) — MOEX ISS prices are not split-adjusted, so indicators run only on the post-split window (VTBR 5000:1-style events).
3. **Fundamental** ([analysis/fundamental.py](analysis/fundamental.py)) — reads static [data/fundamentals.json](data/fundamentals.json) (P/E, debt/EBITDA, ROE, margins, sector; manually maintained, `last_updated` field). `score_fundamental` grades **P/E and ROE relative to sector medians** computed by `get_sector_medians` (sectors with <2 names fall back to the universe-wide median, so singletons aren't graded against themselves). Dividend yield is injected at runtime from the MOEX API, not the JSON. Staleness is enforced in two tiers: `last_updated` older than `FUNDAMENTALS_MAX_AGE_DAYS` (120) logs a warning; older than `FUNDAMENTALS_STALE_DAYS` (240) — or missing/broken — makes `is_fund_stale` exclude the pillar from the final score via the `valid` mechanism (weights renormalize, confidence drops), while the score stays visible in reports. `cbr_rate` (key rate, from macro) feeds a single channel each: it raises the "good" dividend-yield bar (ОФЗ competition) and, when >10%, squeezes the P/E sub-score (higher discount rate → lower fair multiple). Upcoming ex-dividend dates come from `get_upcoming_dividends` (MOEX ISS), merged with a smart-lab.ru scrape fallback (`data/dividend_calendar.py`, `get_upcoming_dividends_smartlab`) — ISS's own endpoint mostly returns past payouts and is frequently empty for the near-term calendar, so smart-lab fills the gap (ISS wins on conflict). The smart-lab table has up to three dates per row (last-buy-day/T+2, registry cutoff, payment date) split across several `<tbody>` blocks; parsing locates the `ticker`/`amount`/`cutoff_date` columns by their stable `order_by_*` href markers in `<thead>` rather than guessing by date order — an earlier "first future date in the row" heuristic silently picked the payment date once the real cutoff had passed, showing a dividend as still-upcoming for weeks after the actual ex-date (caught 2026-07-30). Any parsing failure (network, markup change, missing expected columns) returns `{}`, never raises.
4. **Sentiment** ([analysis/sentiment.py](analysis/sentiment.py)) — pluggable provider via `SENTIMENT_PROVIDER` (`gemini` default | `anthropic` | `none`). `gemini` uses Google Gemini (`gemini-3.5-flash`) with built-in Google Search grounding (`client.models.generate_content` + `types.Tool(google_search=...)`) — chosen for cost; `anthropic` uses Claude `web_search` (pricier, the original path); `none` returns neutral. Each provider's raw text goes through a shared brace-balanced JSON parser; any error/missing key falls back to neutral-50 (never crashes). Keys: `GEMINI_API_KEY` (or `GOOGLE_API_KEY`), `ANTHROPIC_API_KEY`.
5. **Scoring** ([scoring/final_score.py](scoring/final_score.py)) — `build_stock_result()` assembles the final per-stock dict: `compute_final_score` (weighted mean of the three pillars, but pillars that fell back to neutral-50 are **excluded and the remaining weights renormalized** — so a missing sentiment doesn't drag everything toward HOLD), `get_signal` (BUY≥60 / SELL≤35 / HOLD), `get_target_price` (move = conviction `(score−50)/50` × per-horizon volatility, capped ±25% — scales with the stock's own σ, not a flat ±15%), and `assess_confidence` → `high`/`medium`/`low` from pillar agreement + data completeness (surfaced as a dot in the dashboard and a marker in Telegram). `WEIGHTS` is **self-calibrating** ([calibration.py](calibration.py), added 2026-08-01): after every run, `compute_and_save_calibration()` correlates each pillar's historical score against realized 28-day forward return (via `backtest._load_resolved_runs`) and nudges `WEIGHTS` toward whichever pillar actually predicted returns — damped (`LEARNING_RATE=0.2`/cycle, never a full jump), throttled (`MIN_RECALIBRATION_INTERVAL_DAYS=7`), and gated on a minimum sample (`MIN_OBSERVATIONS=60`); a pillar can't be zeroed out (`WEIGHT_FLOOR=0.10`), and if no pillar shows a positive correlation the weights are left untouched rather than guessed. Output lands in `data/calibration.json` — a generated artifact in the same class as `data/history.db` (gitignored, CI-cached across runs via the same cache step) — which `config.py` reads at import time as an overlay on the `_DEFAULT_WEIGHTS` hardcoded fallback; any missing/corrupt/invalid file (wrong keys, negative values, sum≠1.0) silently reverts to defaults, since calibration must never be able to break pipeline startup. This runs fully autonomously (no human approval gate) by explicit choice — see conversation history for the tradeoff discussion. `SIGNAL_THRESHOLDS` are **not** auto-calibrated (kept out of v1 scope, still guesswork); revisit via `evaluate_stored_runs` manually. The technical pillar is a **contrarian/mean-reversion** signal (oversold RSI + proximity to the 52w low score high) — it does not know about broad-market trend. Three guards compensate, all keyed on **ADX/DMI** (`analysis.technical.compute_adx` — Wilder's trend-strength indicator, 0-100, plus `+DI`/`-DI` for direction; `adx_trend_strength` buckets it weak(<20)/moderate(20-40)/strong(>40)), since a binary "below SMA200" flag treats a 1%-under-the-line market the same as a 26%-under-the-line crash: (1) `compute_market_regime` computes ADX on IMOEX itself (needs `data.moex_api.get_index_history`'s HIGH/LOW columns) alongside the bear/bull SMA200 flag; (2) `get_signal`'s `regime`+`trend_strength` params scale the BUY-bar raise — `BEAR_BUY_EXTRA` × `BEAR_TREND_WEAK_MULT`/1.0/`BEAR_TREND_STRONG_MULT` for weak/moderate/strong index-level trend, so a ranging bear market doesn't over-block contrarian buys but a confirmed strong downtrend does; (3) `score_technical` separately dampens the 52w-position pillar's contrarian half (not the RSI pillar, which stays backtest-validated as-is) via `ADX_MODERATE_DOWNTREND_DAMPEN`/`ADX_STRONG_DOWNTREND_DAMPEN` when the **individual stock's own** ADX confirms a downtrend (`minus_di > plus_di`) — this is what stops a single stock like SBER from scoring a contrarian BUY while it's in a confirmed, ADX-strong slide, independent of the market-wide regime. `adjust_target_for_dividend` subtracts a known upcoming payout from the target price when the ex-date falls inside the forecast horizon, since the price gaps down by roughly the dividend right after the cutoff and an unadjusted target overstates upside for a BUY issued right before it.
6. **Report** ([report/claude_report.py](report/claude_report.py)) — `generate_report` writes a Telegram-HTML analyst summary via Claude, with a programmatic `_fallback_report`. `format_full_table` renders the all-stocks table separately.
7. **Delivery** ([report/telegram_bot.py](report/telegram_bot.py)) — splits messages at the 4096-char Telegram limit; `parse_mode=HTML` (only `<b>/<i>/<code>`, no markdown, no `<br>`).

`main.py` `save_results()` writes `reports/analysis_YYYYMMDD.{json,md}`, persists per-ticker run rows to SQLite via [data/store.py](data/store.py) (`save_run`, idempotent per date — for backtest), builds a self-contained HTML dashboard to `docs/index.html` via [dashboard.py](dashboard.py) (`build_dashboard` — latest run + SQLite trend history + backtest, embedded JSON + Chart.js, no server), and logs go to `logs/analysis_YYYYMMDD.log`. CI ([.github/workflows/weekly_analysis.yml](.github/workflows/weekly_analysis.yml)) caches `data/history.db` across runs (so trends/backtest accrue) and publishes `docs/` to GitHub Pages. `docs/` and `*.db` are gitignored (build artifacts). The full Telegram report sends on **every** successful run, not gated to once a week — a prior weekly gate (`has_run_earlier_this_week`) meant a same-week code/data fix (e.g. a stale CBR rate) could compute correctly on Wednesday but not reach Telegram until the following Monday; removed 2026-07-29.

**Startup validation.** `main()` calls `config.validate_config()` first — a `ValueError` on broken `WEIGHTS` (must be non-negative and sum to 1.0) or `SIGNAL_THRESHOLDS` (SELL < BUY) aborts the run before producing wrong signals; missing API keys are non-fatal warnings. Run dates use `config.today_msk()` (UTC+3), since CI runs in UTC.

**Backtest** ([backtest.py](backtest.py), standalone CLI). Two modes: `walk_forward_technical(df, ...)` replays the technical pillar over historical price windows offline (no network, no sentiment — which can't be reconstructed historically) and reports a long-vs-short `edge`; `evaluate_stored_runs(...)` scores past runs from SQLite against realized forward returns once history accrues. This is the harness that answers whether the signals have predictive value — calibrate `WEIGHTS`/`SIGNAL_THRESHOLDS` from its output, not by guesswork.

### Conventions that matter

- **Every stage is failure-isolated.** Each pillar in `_process_ticker` is wrapped in try/except; on error it logs, sets a `meta` fallback flag, and substitutes a neutral score (50) so one bad ticker never aborts the run. A whole-ticker crash is caught in the `run_pipeline` future loop. Preserve this — don't let exceptions propagate out of a stage.
- The dict shape produced by `build_stock_result` is the contract consumed by both report functions. Changing keys there means updating [report/claude_report.py](report/claude_report.py).
- Scores are always clamped to [0, 100]; signals/targets derive from the final score, not the individual pillars.
